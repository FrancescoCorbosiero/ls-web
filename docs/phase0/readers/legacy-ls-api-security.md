## 3. Discrepancies and corrections to the brief (for `docs/plan.md`)

1. **`GET /mono/download-report` (12a G2) also answers 400 on legacy data, not only on a future `from`.** `ReportService.generatePdf` calls `HorizontalPdfGenerator.generateHorizontalPdf(@NonNull @Valid ReportRepr)` through the proxy of a `@Validated` bean (`ls@migration:J/business/service/ReportService.java:42`; `J/business/util/HorizontalPdfGenerator.java:22-25`), so every row is validated: `dataSpedizione` (= `confirmationTs`) `@NotNull`, `importo` `@NotNull @PositiveOrZero`, `peso` `@NotNull @Positive`, `servizio`/`cliente`/`cap` `@NotEmpty` (`J/api/repr/ReportRepr.java:43-74, 77-78`; rows built in `J/business/factory/ReportFactory.java`). A REGISTERED order with `importo` NULL (orders approved before 2024-07-18 and still in tracking PRESA: the fallback at `SpedizioneService.java:194` skips PRESA), or with no `confirmationTs` (orders promoted with `req` absent, `SpedizioneService.java:150`), makes the whole PDF fail with 400 `CONSTRAINT_VIOLATION_400`. 12a G2 and 12c §3 list only the future-`from` case. Consequence: ADM-09 must render a missing amount as "-" and MIG-02 must count such rows (see §6).
2. **12a §3.3 "controller parameter constraint → 400 `ErrorRepr` (inferred)" is only half right.** `WebController` has no `@Validated` (`J/web/WebController.java:24-27`), so Spring MVC 6.1's built-in method validation applies to `@RequestParam @PastOrPresent from` and raises `HandlerMethodValidationException`, a `ResponseStatusException` with status 400 and the framework's own English reason, not the Italian `CONSTRAINT_VIOLATION_400` text (inferred). `CmsController.customerOrders` (`@Validated` class) does give the Italian text. Only the `reason` text differs; the status is 400 in both cases.
3. **12a J: `POST /mono/utils/order/deleteBeforeDate` can never succeed.** `AdminToolsService.deleteOrdersBefore(@PastOrPresent DeleteOrdersBeforeReq req)` (`J/business/service/AdminToolsService.java:63`) puts a date constraint on a DTO type; Hibernate Validator throws `UnexpectedTypeException` on the first call (inferred), which the catch-all turns into 500 before any delete. Not ported anyway (chapter 09 §ADM note), but the "only delivered orders confirmed before" description in 12a J describes unreachable code. Zero log calls per 12a, consistent.
4. **12a §1.2 "Seen in logs", §2.7 log evidence, §2.13 counts, §2.14 secrets table, §5 SEC-06/SEC-07**: NOT CHECKED here (forbidden paths). Nothing read contradicts them; the planner should keep them as 12a's own observations, not as re-verified facts.

## 4. Facts the brief does not mention

* `MethodLoggerAspect` (`J/configuration/MethodLoggerAspect.java:14`, pointcut `execution(* it.logisticasanchez.*.*(..))`, `MonoConstants.java:5`) matches only classes directly in package `it.logisticasanchez`; every class lives under `.mono.`, so the aspect never fires (inferred). Body logging remains the only sensitive logging channel in the application; the Tomcat access log keys `server.tomcat.accesslog.*` exist in `R/application.yml:5-9` (values redacted): if enabled, the query strings of `GET /mono/email-confirm` and `GET /mono/download-report` (e-mail and verification code) are logged there as well, and by nginx in any case.
* `JwtAuthFilter` is a `@Component` (`JwtAuthFilter.java:21-24`), so Boot also registers it as a plain servlet filter outside the security chain; `OncePerRequestFilter` makes the second pass a no-op (inferred). Harmless, but it means the filter order is not what `addFilterAfter` alone suggests.
* `EmailNotificationReq.content` is limited to 255 characters (`J/api/req/EmailNotificationReq.java:29-30`) and `sendHtml` declares `@Valid` (`AwsEmailService.java:52`), which would reject every HTML template; it is bypassed because `sendNotification` and `sendAdminNotification` call `sendHtml` by self-invocation (`AwsEmailService.java:129, 134`, no proxy). Only `/mono/sendEmail` (external call of `send`) is actually limited.
* The audit columns `create_user`/`update_user` of every business table hold the first granted authority (`"ROLE_ADMIN"`) or the literal `"CUSTOMER"` when no staff token is present (`J/persistence/audit/SpedizioneAuditListener.java:18, 24`, same in the other three listeners; `SecurityContextUtils.java:26-37`). No staff user id is ever stored: the migration cannot attribute legacy actions to a person.
* Dead or unused code: `@EnableCaching` with no `@Cacheable` anywhere (`CacheConfig.java`; grep), the `JsonSchemaGenerator` bean (`JacksonConfig.java:20-23`), `SpedizioneService.reportList(String)` (PENDING filter, `:198`), `SpedizioneService.state(String)` and `getAll()`, `ReportUtil.report` (older two-column PDF), `AwsEmailService.sendHtml(req, pdfBytes)` (inline base64 "attachment"), `ErrorEnum.GENERIC_401/403/503` paths other than refresh. The `mvc.pathmatch` key sits at the top level of `R/application.yml:44-46`, outside `spring:`, so it is ignored.
* The 6-month window is computed as `LocalDateTime.now().minusMonths(6).toInstant(ZoneOffset.UTC)` (`SpedizioneRepository.java:43`): server-local time read as UTC, so the window edge shifts by the Rome offset (1–2 h). Negligible, but the new app should define the window in one place with an explicit zone if it keeps one.
* `A2` refresh: `deleteById` of an unknown session id is a no-op in Spring Data JPA 3 (inferred), so the 403 is clean; a deleted user with a live session row also gets 403 (`AuthenticationService.java:66-67`).
* The expired-token 401 body is the raw jjwt message (includes the token's expiry instant and the allowed clock skew); the "Access Denied" string reaches clients only when `hideDetail` is false.
* `OrderService.updateOrder` with `req` absent throws NPE → 500 (`OrderService.java:205-211`); `SpedizioneService.detail` NPEs when an order has no `dettaglioColli` row (`:186-187`), which a hand-edited database could produce.
* Report rows: for an undelivered order the "Dt/Cons." column shows `updateTms`, and `shippingTs` falls back to `confirmationTs` (`SpedizioneService.java:224-229`): the legacy PDF's delivery date is not a delivery date for open orders. ADM-09 should print "-" instead (ADR note).

## 6. Risks and unknowns

* **Which build is live** (12a §6): the P-02 fingerprints hold in the code read (`orElse(NON_GESTITO)`; custom `ObjectMapper`). Still unknown.
* **Production values** of `app.allowed-origins`, `app.email.origin`, `app.jwt.*`, `app.error.hideDetail`, `server.tomcat.accesslog.enabled` (Q-50, P-03): redacted here; only key names verified.
* **Database collation** (CU-02, CU-03, CU-17): every lookup is SQL equality (`SoggettoRepository.java:15-22`, `SpedizioneRepository.java:22-34`); the new app must pick its own rule (TRK-02 default case-insensitive, trimmed).
* **Legacy data that breaks the legacy report** (§3 item 1): REGISTERED orders with `importo` NULL, `confirmation_ts` NULL, `peso` 0 or `dettaglio_colli` missing. MIG-02's reconciliation must count them; ADM-09 must tolerate them.
* **Duplicate customer e-mails** (`SOGGETTI` unique only on `ragione_sociale, email, codiceVerifica`, `SoggettoEntity.java:15-17`): every e-mail lookup returns `Optional` → 500 today; MIG must merge or flag (CUS-01 keys on e-mail).
* **Staff accounts** (Q-17): number, roles, `policy` values unknown; not imported by ADM-01's design — confirm with the owner that staff will be recreated.
* **Open endpoints and e-mailed links** (SEC-01…03, SEC-19): verification codes and e-mails travel in `GET` query strings → in access logs and browser history; after cut-over the 410 page must answer uniformly (same status and body for known and unknown e-mails) so it cannot be used as an oracle.
* **Verification of 12a's log- and secret-based claims** (SEC-06, SEC-07, log counts): out of scope by rule; not re-verified.
