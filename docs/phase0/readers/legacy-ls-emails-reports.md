## 3. Discrepancies and corrections to the brief (for `docs/plan.md`)

1. **12c §3.4 col 4 "Dt/Cons."**: for delivered orders it is the stored `shippingTs`, re-stamped on every TRANSITO (`SpedizioneService.java:246`), not "the time the order first left PRESA". Wording only; the column is still not the delivery time (`deliveryTs` is never printed).
2. **12c §4.2 / 09 ADM-04 "`importo` required"** holds only when the body carries `req`. `OrderConfirmationReq.req` is optional (`OrderConfirmationReq.java:22`, no `@NotNull`); with `req` absent, `SpedizioneService.confirm` takes the `promote` path (`:150`): the order becomes REGISTERED **with its `TEMP…` code, no amount, tracking still NON_GESTITO and no `confirmationTs`**, and L-E6 is sent with subject "Conferma ordine N. TEMP…" (`OrderService.java:117-119`). Such an order later breaks the customer's whole report download (`ReportRepr.ReportRow.dataSpedizione` `@NotNull`, `ReportRepr.java:43-45`). The CMS always sends `req`, so this is a Postman-only path, but migration (08 DQ-13) must expect REGISTERED rows with TEMP codes and null `importo`/`confirmationTs` and treat them explicitly.
3. **12c §3.6 / §3.7 understate the report endpoint**: `POST /mono/cms/order/report` is unauthenticated and `email` need not be a customer's, so with `sendToCustomer=true` **anyone can make the company's SES identity send a "Report ordini" e-mail with `{origin}` links to any address** (`CmsController.java:79-106`; `ReportReq.java:20-23` only checks the address syntax). Add to the Q-21 nginx block list and to the cut-over risk register, next to `/mono/sendEmail`.
4. **12c §1.6 / 09 EML-09**: the delivery e-mail prints `note` (`T/tracking-state.html:103-104`), the same field staff edit from the CMS notes dialog (`OrderService.java:181-203`, `/cms/notes/update`). Internal notes written after approval reach the customer at delivery. 09 says "no internal notes" only for the report (ADM-09); EML-09 needs the same rule or a separate staff-only note field (12b owns the model).
5. **12c §1.2 L-E7 recipient**: `OrderService.decline` checks that `email` is a customer (`:140`) but never that the order belongs to that customer (`:141`): staff can decline order X and notify customer Y. The new ADM-04 decline must derive the recipient from the order.
6. **12c §0 alias table**: the comparison with `dev_API_v2` cannot be re-verified from this clone (single branch); keep it as 12c's claim, not a Phase 0 fact.
7. **Date of the `importo` requirement**: the sibling 12c chapter reader (its §6 item 2) records 12a as saying 2024-07-18 (`d7b2c56`); `git log -S` on the exact `requireNonNull(patchReq.getImporto())` string names only `d7732eb` (2024-07-16). DQ-13 should use 2024-07-16 as the earliest date from which `importo` is reliably non-null, unless 12a's reader checked a different string.
8. **12c §5.4 "255-character limit bypassed"** has a porting consequence 12c does not draw: every HTML body is far longer than `EmailNotificationReq.content` allows (`:28-30`); the limit is a bug, not a rule. The new outbox must not carry it.
9. **Chapter 09 EML table**: consistent with the code (L-E1…L-E10 mapping, "sent on every click" for L-E2, EML-09 = L-E8). Nothing to correct beyond items 2, 4 and 5 above. 09 ADM-09's "customer block and 13 columns" and "office always receives it" match `HorizontalPdfGenerator.java:72-222` and `CmsController.java:106`.

## 4. Facts the brief does not mention

* Templates are rendered **before** the kill switch is consulted (`EmailReqFactory` runs, then `sendHtml` returns at `AwsEmailService.java:53`): template errors surface even with e-mails disabled. Useful for tests, irrelevant for parity.
* `NotificationEnum` labels, unused as subjects, are a ready-made Italian naming of the notification kinds: "Conferma indirizzo email", "Indirizzo email e/o dati cliente rifiutati dall'amministratore", "Indirizzo email e dati clienti confermati", "Richiesta Dettaglio Ordine", "Ordine invalido rifiutato dall'amministratore", "Report ordini", "Report ordini per admin", "Stato ordine" (`NotificationEnum.java:16-23`).
* `AdminNotificationEnum.fromString` returns an `EvasioneEnum` (`:27-34`): the admin-notification labels can never be parsed back from JSON (copy-paste bug, harmless at runtime).
* `order-detail.html` and `tracking-state.html` declare `<html lang="en">` (`:2`) for Italian content; `email-confirmation.html` has a viewport meta, the others none; all CSS is a `<style>` block (no inlining), which many clients drop (inferred).
* `trace` refuses tracking changes on orders that are not REGISTERED with a 500 (`SpedizioneService.java:239`); `TraceReq.tracking` is the enum ordinal (`TraceReq.java:22-23`, `TrackingState.fromId`).
* `SpedizioneService.reportList` mutates managed entities (`setShippingTs`) inside a stream `peek` (`:224-229`) with no transaction, so nothing is flushed (inferred) but the design is fragile; the new report must compute the column, not patch the entity.
* With no `from`, `LocalDate.MIN` is converted to an `Instant` for a `createTms BETWEEN` query (`:212-215, :219-223`); whether MySQL accepts a year −999999999 is NOT CHECKED. The file name then carries that year (`ReportUtil.java:122-126`).
* `WebController` is not `@Validated`, so `@PastOrPresent` on `/download-report`'s `from` (`:41`) is inert there; the same check on `ReportService.generatePdf` (`:24, :34`) is what produces the 400.
* `/cms/order/update` rejects a code already in use **including the order's own** (`OrderService.java:208-209`): resending an unchanged code answers 409 (inferred).
* Personal data in source: a code comment at `EmailReqFactory.java:24` and the fixture at `NonRegressionTests.java:73` contain a real personal e-mail address (not reproduced). Add to the Q-53 inventory; never port these lines or the test data.
