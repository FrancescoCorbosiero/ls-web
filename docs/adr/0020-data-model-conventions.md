# 0020 · Data model conventions

* **Status:** Accepted
* **Date:** 2026-10-17
* **Requirement IDs:** ADM-10, ADM-01, NFR-02, NFR-03; carried by every M1 ID that stores data (CUS-01…CUS-06, ADM-02…ADM-09, PUB-11, EML-01…EML-09, TRK-02) · **Questions:** Q-52, Q-55 (owner decisions), Q-05, Q-06, Q-09, Q-11, Q-18, Q-24, Q-25, Q-28, Q-36 (defaults applied as columns and constraints) · **Findings:** 08 §2.1–2.5 amended by 12b §5.4, plan §4.4, §8.1, D-88

## Context

Chapter 08 §2 defines the target model of the new app; 12b §5.4 amends it from the backend
source; `docs/plan.md` §4.4 adds the tables chapter 08 names without columns (`email_outbox`,
`report_run`, `feature_flag`) and a table for a declined customer's re-registration data
(D-88, Q-09). Chapter 10 §2 fixes money (`numeric(10,2)` plus a VAT flag) and time
(`timestamptz`, shown in Europe/Rome). Chapter 08 was written for a migration of the legacy
MySQL data: a third of its columns exist only to carry legacy ids, raw values, data-quality
flags and import bookkeeping.

**Owner decision Q-55 (2026-10-17): no migration of the legacy data.** The new app starts
with an empty database. MIG-01…MIG-03 are dropped; there is no `migration` module, no
importer, no `legacy_key_map`, `import_run` or `import_issue`, and the owner asked not to
over-complicate the design. The schema therefore keeps only what the M1 requirements of
chapter 09 need, and every rule chapter 08 relaxed "for legacy rows" is enforced strictly:
no row will ever violate it.

The schema is the first Flyway migrations of Phase 1 stage 2 (`docs/plan.md` §5 item 4;
`docs/phase1/log.md`). Only the integrator writes migrations (`docs/plan.md` §6).

## Decision

### Engine, tool and files

* **PostgreSQL 16** (ADR 0001, Q-52), one database, one schema (the connection's default
  schema; migrations never qualify names, so the tests can apply them to a schema of their
  own). **Flyway** with strictly sequential, forward-only versions `V001__…`; a merged
  migration is never edited; `ddl-auto: validate` in every profile; `clean` disabled.
* One migration per area: `V001` conventions (the `set_updated_at()` trigger function),
  `V002` `staff_user`, `V003` `customer`, `customer_pending_registration`, `customer_user`,
  `login_token`, `V004` `tracking_state`, `accessory_service`, `V005` `shipment_order`,
  `order_line`, `order_internal_note`, `tracking_event`, `V006` `lead`, `V007`
  `email_outbox`, `report_run`, `V008` `feature_flag`, `audit_log`, `audit_log_detail` with
  the immutability trigger, `V009` seeds. Every table and every non-obvious column carries
  a `COMMENT ON` (asserted by `SchemaConformanceIT`).

### Column conventions

| Topic | Rule |
|---|---|
| Keys | `bigint GENERATED ALWAYS AS IDENTITY`. Exceptions: the two seeded enumerations keep the legacy ids as their primary key (`tracking_state.id smallint` 0–5; `accessory_service.id integer GENERATED BY DEFAULT AS IDENTITY`, seeded 0–5 and restarted at 6 for ENH-14); `feature_flag.key` is a natural key; one-row-per-parent tables (`order_internal_note`, `audit_log_detail`, `customer_pending_registration`) use the parent id as their primary key. |
| Time | `timestamptz` everywhere, UTC in the database (`hibernate.jdbc.time_zone: UTC`), Europe/Rome in the UI. `created_at`/`updated_at` default to `now()`; `updated_at` is maintained by the `set_updated_at()` trigger on every table that has it (`staff_user`, `customer`, `shipment_order`, `email_outbox`, `feature_flag`), whichever client writes. JPA entities map them to `Instant`. |
| Money | `numeric(10,2)` in EUR plus `shipment_order.amount_vat_included boolean` (Q-05 seam: the service sets it from `ls.orders.amount.vat-included-default`, never guessed by the schema). Weights `numeric(9,2)`/`numeric(12,2)`, volumes `numeric(10,2)`. |
| Enumerations as rows | The two legacy enumerations are tables seeded exactly from 12b §2.2 (ids, names, labels, declaration order; `is_none` only on service 0): `tracking_state` (plus `public_title` and `step_label` from chapter 06 §5.7 for the public page) and `accessory_service`. Read-only in M1; the compatibility endpoints serve them unchanged (API-02). |
| State columns | `varchar` with a named CHECK (`ck_<table>_<column>`) listing exactly the states of chapter 08 §2.4: `customer.status` (`PENDING_VERIFICATION`, `PENDING_APPROVAL`, `ACTIVE`, `DECLINED`), `shipment_order.status` (`PENDING`, `APPROVED`, `DECLINED`), `lead.status` (`NEW`, `CONTACTED`, `WON`, `LOST`, `SPAM`), `email_outbox.status` (`QUEUED`, `SENT`, `FAILED`), `login_token.purpose`, `customer_user.role`, `staff_user.role`, `tracking_event.source` (`APPROVAL`, `STAFF`, `BULK`), `audit_log.actor_type` (`STAFF`, `CUSTOMER`, `SYSTEM`), `*.source` (`CUSTOMER_AREA`, `BACKOFFICE`). JPA maps them with `@Enumerated(STRING)` on a `varchar` column (no native enum type). |
| Code lengths | `shipment_order.code varchar(255)` as `docs/plan.md` §7.1 D-09 asks (chapter 08 §2.3 says 64). D-09's reason (legacy codes up to 255 characters) is moot under Q-55, so the column could be 64; the plan's figure is kept because it costs nothing and the approval form (Phase 2, ADM-04) sets the practical maximum. `temp_code varchar(64)` (`TEMP-` + 8 characters), `transport_document_code varchar(100)` as chapter 08. Amended 2026-10-17 after the stage 2 verification (the first attempt had 64 without recording it). |
| Normalised uniqueness | E-mails are stored trimmed and lower-case (`ck_*_email_normalised`) and unique on `lower(btrim(email))` (`ux_customer_email`, `ux_customer_user_email`, `ux_staff_user_email`). Codes are stored as typed, trimmed, and unique on `lower(btrim(code))` (`ux_shipment_order_code`, `ux_shipment_order_temp_code`; Q-06: case-insensitive, no sequence assumed). `staff_user.username` is stored lower-case and unique. |
| State consistency | CHECKs that a terminal state carries its data: `ck_customer_active_is_verified_and_approved` (ACTIVE ⇒ `email_verified_at` and `approved_at`; Q-28), `ck_customer_pending_approval_is_verified`, `ck_customer_declined_has_time`, `ck_shipment_order_approved_is_complete` (APPROVED ⇒ `code`, `amount`, `approved_at`), `ck_shipment_order_declined_has_time`, `ck_shipment_order_pending_has_no_outcome`, `ck_login_token_subject` (REGISTER ⇔ no customer user and an `email_hash`), `ck_email_outbox_queued_has_body`, `ck_email_outbox_sent_has_time`, `ck_email_outbox_token_pair`, `ck_report_run_range` (`date_from ≤ date_to`). |
| Input rules at the column | Five-digit CAP on `customer`, `customer_pending_registration` and both order snapshots (`^[0-9]{5}$`); `order_line` dimensions ≥ 1, `weight_kg > 0`, `quantity ≥ 1` (Q-35 integers); `shipment_order.amount ≥ 0` (the > 0 rule of approval lives in the service, so the owner can allow 0 without a migration); `package_count ≥ 0`; `order_internal_note.body ≤ 5 000` characters; `lead.message ≤ 5 000`; a quote lead has a phone; `feature_flag.key` and `audit_log.action` are dotted lower-camel names; `email_outbox.kind` is an `EML-0x` id. |
| Indexes | Planned queries: `customer (status)`, `(created_at)`; `customer_user (customer_id)` plus `ux_customer_user_one_owner` (one OWNER per customer, Q-11); `login_token (customer_user_id)`, `(expires_at)`; `shipment_order (customer_id, created_at desc)`, `(status)`, `(tracking_state_id)`, `(created_at)`, `ux_shipment_order_idempotency_key`; `tracking_event (order_id, occurred_at desc, id desc)`; `lead (status, created_at desc)`, `(retain_until)`, `(customer_id)`; `email_outbox` partial `(next_attempt_at) where status = 'QUEUED'`, `(status, created_at)`, purge index on sent rows with bodies; `report_run (customer_id, created_at desc)`, `(created_at)`; `audit_log (occurred_at)`, `(entity_type, entity_id)`, `(actor_type, actor_id)`. |
| Deletion | No `ON DELETE CASCADE` anywhere: erasure is anonymisation (chapter 10 §5, ADR 0024), never a cascade. |

### What changed from chapter 08 §2.3 under Q-55

Dropped (no legacy row will exist): `legacy_id`, `legacy_email_raw`, `legacy_payload`,
`legacy_stato`, `legacy_tracking_raw`, `legacy_service_raw`, `amount_raw`,
`legacy_type_raw`, `legacy_json`, `accessory_service.legacy_id`, every `data_quality`
column, `order_internal_note.imported_from_legacy`, `tracking_event.time_is_estimated`, the
`LEGACY` value of `source`, `LEGACY_IMPORT` of `tracking_event.source`, `IMPORT` of
`audit_log.actor_type`, and the tables `legacy_key_map`, `import_run`, `import_issue`.
`SchemaConformanceIT` fails if any `legacy_*`, `*_raw` or `data_quality` column reappears.

Tightened (chapter 08 relaxed them "for legacy rows only"): `customer.phone` NOT NULL (Q-36),
`customer.registered_at` NOT NULL, `postal_code` five digits, `shipment_order.
transport_document_code` NOT NULL (Q-24), `submitted_at` NOT NULL, APPROVED orders always
carry `code`, `amount` and `approved_at`, `order_line` dimensions ≥ 1 and quantity ≥ 1,
`order_internal_note.updated_by` NOT NULL, `tracking_event.staff_user_id` stays nullable
(system-written `APPROVAL` events).

Added (plan §4.4, D-88): `customer_pending_registration` (the re-registration data of a
DECLINED customer, one row per customer, applied when the verification link is used and
then deleted — Q-09); `email_outbox` (kind, recipient, Reply-To, subject, text and HTML
bodies, `login_token_id` + `token_ciphertext` for one-time links, status, attempts,
`next_attempt_at`, `last_error`, `sent_at`, `provider_message_id`, `bodies_purged_at`);
`report_run` (customer, requesting staff user, inclusive date range, `only_delivered`,
`send_to_customer`, the `recipients` actually used, `row_count`; no stored file — the PDF is
regenerated for the authenticated download, ADR 0001); `feature_flag` (`key`, `enabled`,
`requirement_id`, `updated_by`, `updated_at`; ADR 0025); `shipment_order.package_count`,
`amount_vat_included`, `customer_user.role` (plan §8.1). `tracking_state.public_title`
and `step_label` hold the public page's texts as chapter 08 says; the tracking module may
override them through message keys (Q-04 seam) without a migration.

Simplified: hashes (`token_hash`, `email_hash`, `requested_ip_hash`, `ip_hash`) are
`varchar(64)` hex with a length CHECK instead of `char(64)` (identical content, friendlier
to JDBC and Hibernate validation); `accessory_service` has no `legacy_id`/`legacy_json`:
its `id`, `name` and `label` *are* the EP-20 item.

### Audit log immutability (NFR-02)

`audit_log` and `audit_log_detail` accept INSERT only, enforced in the database so it holds
for every client with a single application role:

* the trigger function `audit_log_immutable()` (`BEFORE UPDATE OR DELETE`, both tables)
  raises `insufficient_privilege` on every UPDATE and on every DELETE that is not part of a
  **maintenance transaction**, i.e. one that ran `SET LOCAL ls.audit_maintenance = 'on'`;
* the retention job (audit log 24 months, Q-18) and the erasure tool (NFR-03, which deletes
  the personal values in `audit_log_detail`) are the only code paths that set it, each in
  its own transaction; nothing else in the app does (a test in Phase 3 greps for it);
* **production option, in addition:** `REVOKE UPDATE, DELETE ON audit_log, audit_log_detail
  FROM <application role>` and a separate maintenance role with `DELETE` that the retention
  job and the erasure tool use through their own datasource. The trigger stays, so the
  behaviour is the same in every environment; the grants only add defence in depth. The
  `deploy/` stage documents the roles in the bootstrap script.

`MigrationsIT` (`NFR-02`) asserts: UPDATE refused always; DELETE refused outside, allowed
inside a maintenance transaction, on both tables.

### Seeds and what is never seeded

`V009` seeds the six tracking states and the six accessory services (ADM-10, Q-25) and the
25 feature-flag keys of chapter 09 §M2, all off (ADR 0025). **No migration ever inserts a
staff user, a customer or an order** (ADM-01): `NoSeededStaffAccountsTest` and
`NoSeedDataOutsideLocalAndTestProfilesTest` (`ADM-01`) parse the migrations and the
configuration and fail otherwise; demo data come only from the `dev-seed` command of the
`local` profile (synthetic values, random passwords).

### Seams (defaults the owner may still change)

| Default | Where it lives |
|---|---|
| Q-05 VAT flag default | `ls.orders.amount.vat-included-default` (service); the column only stores the flag |
| Q-06 code uniqueness ignoring case | `ux_shipment_order_code` on `lower(btrim(code))`; a case-sensitive rule would be a new migration |
| Q-09 re-registration stored apart | `customer_pending_registration` |
| Q-11 one login per customer | `ux_customer_user_one_owner`; `MEMBER` already allowed by `ck_customer_user_role` |
| Q-24 transport document required | `transport_document_code NOT NULL` (relaxing it = one migration) |
| Q-28 only verified customers approved | `ck_customer_active_is_verified_and_approved` |
| Q-36 phone required | `customer.phone NOT NULL` |
| Q-18 retention | the jobs; the schema offers `lead.retain_until`, `email_outbox.bodies_purged_at`, `login_token.expires_at`, `audit_log.occurred_at` |

## Consequences

* Simpler model: 17 tables, no import bookkeeping, no raw columns; every table is covered
  by `SchemaConformanceIT` (type and nullability of every column, every CHECK, unique
  constraint and unique index of this ADR, the audit triggers, a comment on every table).
* Phase 2 modules build their entities on these tables and ask the integrator for any
  change as a new migration (`docs/plan.md` §6); Phase 1 owns the entities of `staff_user`,
  `customer_user`, `login_token`, `feature_flag`, `audit_log`, `audit_log_detail`,
  `email_outbox` (packages `auth`, `platform.flags`, `platform.audit`, `notifications`).
* Strict CHECKs mean the services must validate first and translate a violation into the
  422/409 of the error model (ADR 0002), never a 500; the tests of each module cover that.
* The owner's remaining choices (Q-05, Q-06, Q-24, Q-36 …) are one-line migrations or
  settings; none requires a data migration.
* The staff one-time set-password link of ADM-01 needs its own token row: the auth stage
  (stage 6) adds it as the next migration (`staff_setup_token` or a purpose on a shared
  table), recorded in ADR 0003.
* Hibernate 7 validation accepts `timestamptz`↔`Instant`, `jsonb`↔`@JdbcTypeCode(JSON)
  String`, `bytea`↔`byte[]` and `varchar`↔`@Enumerated(STRING)` as mapped here
  (`PhaseOneEntitiesIT` writes and reads every Phase 1 entity).
